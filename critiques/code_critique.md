# Codebase Analysis: rms-metadata-tools

Generated by reading every file and every line of source, tests, cloud configs, scripts,
and templates. Follows the `python-codebase-analysis` skill template with project rules from
`.cursor/rules/` as the authoritative standards.

---

## Summary

The codebase is well-structured with a clean src-layout, strong test coverage of the hermetic
(non-SPICE) paths, and consistent use of `PdsLogger` and `FCPath` throughout most of the
library. The three highest-priority issues are: (1) **six `open()`/`read_text()`/`write_text()`
calls without `encoding=`** that will break on non-UTF-8 platforms or with Windows-generated
files; (2) a **duplicate tile in `OUTER_RING_TILES`** that silently produces duplicate
subregion rows in every outer-ring detailed geometry file; and (3) **CI linting that runs only
on Python 3.13**, leaving 3.11 and 3.12 type or lint regressions undetected. Fifteen additional
medium-severity findings follow.

## 1. Structure and Layout

### 1.1 — `events.log` runtime artifacts in the source tree [LOW]

**Evidence**: `src/metadata_tools/events.log` and `src/metadata_tools/hosts/GO_0xxx/events.log`
exist on disk and contain JSON exception traces from `rms-cloud-tasks`. They are listed in
`.gitignore` (`*.log`) so are not committed, but their presence in `src/` means a `pip install -e .`
wheel could accidentally include them if the package-data glob were broadened.

**Suggestion**: Configure `rms-cloud-tasks` to write its event log to a path outside the source
tree (e.g. `logs/`, the project root, or `$XDG_STATE_HOME`). Add `logs/` to `.gitignore`. No
source change is needed unless the log path is hard-coded — check `rms-cloud-tasks` docs for the
`events_log` config option.

## 2. Best Practices Alignment

### 2.1 — Six `open()`/`read_text()`/`write_text()` calls without `encoding=` [HIGH]

**Rule**: `python.mdc` §"Encoding and I/O": "explicit `encoding='utf-8'` on `open()` calls
(platform default varies)." PEP 597 (Python 3.10+) warns that the platform default is not
always UTF-8.

**Evidence**:

| File | Line | Call | Fix |
|------|------|------|-----|
| `src/metadata_tools/__init__.py` | 28 | `_env_file.open()` | `_env_file.open(encoding='utf-8')` |
| `src/metadata_tools/cli/_host.py` | 182 | `template_path.read_text()` | `template_path.read_text(encoding='utf-8')` |
| `src/metadata_tools/cli/_host.py` | 261 | `open(config_path)` | `open(config_path, encoding='utf-8')` |
| `src/metadata_tools/cli/geometry_cloud.py` | 83–86 | `Path(...).write_text(...)` | add `encoding='utf-8'` |
| `src/metadata_tools/cli/index_cloud.py` | 80–83 | `Path(...).write_text(...)` | add `encoding='utf-8'` |
| `src/metadata_tools/cli/cumulative_cloud.py` | 70–73 | `Path(...).write_text(...)` | add `encoding='utf-8'` |

**Self-contained fix instructions for a fresh AI agent**:

In `src/metadata_tools/__init__.py`, change line 28:
```python
# Before
    with _env_file.open() as _f:
# After
    with _env_file.open(encoding='utf-8') as _f:
```

In `src/metadata_tools/cli/_host.py`, change line 182:
```python
# Before
    return f'#!/bin/bash\n{header}\n{template_path.read_text().rstrip()}\n\n{worker_cmd}\n'
# After
    return f'#!/bin/bash\n{header}\n{template_path.read_text(encoding="utf-8").rstrip()}\n\n{worker_cmd}\n'
```

In `src/metadata_tools/cli/_host.py`, change line 261:
```python
# Before
        with open(config_path) as cfg_f:
# After
        with open(config_path, encoding='utf-8') as cfg_f:
```

In each of `geometry_cloud.py` (line 83), `index_cloud.py` (line 80), `cumulative_cloud.py`
(line 70), the pattern is:
```python
# Before
        Path(create_startup_file).write_text(
            build_startup_script(...)
        )
# After
        Path(create_startup_file).write_text(
            build_startup_script(...),
            encoding='utf-8',
        )
```

## 5. Performance and Resource Use

### 5.1 — Module-level `for` loops in `columns/body.py` and `columns/ring.py` run at import [MEDIUM]

**Evidence**:
- `src/metadata_tools/columns/body.py`: `BODY_TILES`, `BODY_TILE_DICT` built in module-level
  for-loops at import time.
- `src/metadata_tools/columns/ring.py`: `RING_TILES`, `RING_TILE_DICT`, `OUTER_RING_TILES`,
  `OUTER_RING_TILE_DICT` built at import.

These run `util.replace()` (which recurses through nested tuples) for every body name, for
every import of the package — including in tests.

The `columns/__init__.py` already uses lazy initialization via `get_body_summary_dict()` and
`get_body_detailed_dict()`, but the underlying tile dicts are still eager.

**Suggestion**: Wrap the module-level for-loops in a `functools.lru_cache`-decorated function:
```python
@functools.lru_cache(maxsize=None)
def _build_ring_tile_dict() -> dict[str, Any]:
    return {body: util.replace(RING_TILES[body], defs.BODYX, body)
            for body in defs.BODY_NAMES}
```
This keeps the logic identical but defers execution until first use.

## 6. Maintainability and Extensibility

### 6.1 — `locals()['link_' + link]` dynamic lookup in `record.py` [HIGH]

**Evidence**: `src/metadata_tools/geometry_support/record.py:210`:
```python
            link_fn = locals()['link_' + link]
```

This resolves nested functions `link_null` and `link_one` at runtime via a string
concatenation into `locals()`. If either function is renamed, the code silently breaks
at runtime (KeyError rather than a static NameError). It also prevents mypy from type-
checking the dispatch.

**Self-contained fix for a fresh AI agent**: Open
`src/metadata_tools/geometry_support/record.py`. Find the `postprocess()` method (around
line 190). It defines `link_null` and `link_one` as inner functions and then dispatches with
`locals()['link_' + link]`. Replace the dynamic lookup with an explicit dict:

```python
# Inside postprocess(), after defining link_null and link_one:
_link_dispatch: dict[str, Callable[..., Any]] = {
    'null': link_null,
    'one': link_one,
}
...
# Replace:
#   link_fn = locals()['link_' + link]
# With:
link_fn = _link_dispatch[link]
```

This is statically type-checkable and will raise a `KeyError` (not a `locals()` oddity) if an
unknown link type is used.

### 6.3 — `index_config.py` suppresses exception chain with `from None` [HIGH]

**Evidence**: `src/metadata_tools/hosts/GO_0xxx/index_config.py:120`:

`from None` discards the original exception context. If the original `FileNotFoundError`

## 7. Security and Robustness

### 7.1 — Duplicate tile in `OUTER_RING_TILES` [HIGH]

**Evidence**: `src/metadata_tools/columns/ring.py:166` and `ring.py:170`:
```python
        ("where_between", RING_AZ, 0.80 * np.pi, 1.20 * np.pi),   # line 166
        ("where_between", RING_AZ, 1.20 * np.pi, 1.45 * np.pi),   # line 167
        ("where_between", RING_AZ, 1.45 * np.pi, 1.55 * np.pi),   # line 168
        ("where_between", RING_AZ, 1.55 * np.pi, 1.80 * np.pi),   # line 169
        ("where_between", RING_AZ, 0.80 * np.pi, 1.20 * np.pi),   # line 170 — DUPLICATE!
```

Line 170 is identical to line 166. Compare to `RING_TILES` (lines 144–155) where the
corresponding entry is:
```python
        ("where_between", RING_AZ, 0.80 * np.pi, 1.20 * np.pi),   # line 148
```
`RING_TILES` ends with a `where_any` clause but `OUTER_RING_TILES` appends the duplicate
at line 170 before its own `where_any`. This produces two identical subregion rows in every
outer-ring detailed geometry file.

**Self-contained fix**: Open `src/metadata_tools/columns/ring.py`. On line 170, determine
what the correct azimuth range should be. If the intent was to extend the tile sequence past
`1.80 * np.pi` symmetrically (the outer ring continues around the other side), the duplicate
should either be removed or replaced with the correct bounds. If it was meant to be a different
segment (e.g. `1.80 * np.pi` to `2.00 * np.pi`), update accordingly. Then add a test in
`tests/columns/test_ring.py` that asserts tile bounds are unique:
```python
def test_outer_ring_tiles_no_duplicates(ring_module: ModuleType) -> None:
    for body, tiles in ring_module.OUTER_RING_TILE_DICT.items():
        assert len(tiles) == len(set(map(tuple, tiles))), f'{body} has duplicate tiles'
```

### 7.2 — `bodies_select.inventory()` broad exception catch [HIGH]

**Evidence**: `src/metadata_tools/geometry_support/bodies_select.py` — the `inventory()`
function catches `(AssertionError, AttributeError, IndexError, KeyError, LookupError,
TypeError, ValueError)`. This swallows programming errors (e.g. a `TypeError` from a
refactored function signature) alongside the intended SPICE runtime errors.

**Suggestion**: Narrow the catch. SPICE errors typically manifest as `RuntimeError` with
a `SPICE(...)` prefix in the message. Consider:
```python
try:
    result = record.observation.inventory(bodies, expand=config.EXPAND, cache=True)
except RuntimeError as exc:
    if 'CKINSUFFDATA' in str(exc) or 'SPICE' in str(exc):
        record.pointing_available = False
        return []
    raise  # re-raise unexpected RuntimeErrors
except (AttributeError, TypeError) as exc:
    logger.exception('Unexpected error in inventory: %s', exc)
    return []
```

Alternatively, check whether `cspyce` exposes a typed base exception class and catch that.

### 7.3 — `label_support.py:34` — `filepath.exists()` pre-check violates filecache rule [MEDIUM]

**Rule**: `filecache.mdc`: "Prefer try/except `FileNotFoundError` over `exists()` pre-checks."
An `exists()` check followed by an operation introduces a TOCTOU race and does not work
reliably with cloud paths.

**Evidence**: `src/metadata_tools/label_support.py:34`:
```python
    if not filepath.exists():
        return
```

**Self-contained fix**: Open `src/metadata_tools/label_support.py`. The `create()` function
checks `filepath.exists()` before rendering the template. Change the pattern to:
```python
try:
    # existing code that reads the file
except FileNotFoundError:
    return
```
or, if the function just early-returns without reading the file, catch the `FileNotFoundError`
that the template rendering itself would raise.

### 7.4 — `index_support/table.py:83` — `primary_index_label_path.exists()` pre-check [MEDIUM]

**Rule**: Same as 7.3.

**Evidence**: `src/metadata_tools/index_support/table.py:83`:

```python
            if not self.primary_index_label_path.exists():
```

## 8. Dependencies and Tooling

### 8.1 — CI lint job runs only on Python 3.13 [HIGH]

**Evidence**: `.github/workflows/run-tests.yml` has:
```yaml
    - name: Lint
      if: matrix.python-version == '3.13'
      run: ...
```

This means ruff and mypy are only exercised on 3.13. Type regressions that only affect
3.11 or 3.12 (e.g. a `list[str]` vs `List[str]` issue, or a stdlib change) would pass CI.

**Self-contained fix**: Remove the `if: matrix.python-version == '3.13'` condition from the
lint step so it runs on all matrix Python versions. Alternatively, run lint in a separate job
that runs on 3.11 only (the minimum supported version where a regression is most likely to
first appear).

### 8.2 — CI uses `PYPI_API_TOKEN` instead of Trusted Publishers [MEDIUM]

**Evidence**: `.github/workflows/publish_to_pypi.yml`:
```yaml
      - name: Publish package
        uses: pypa/gh-action-pypi-publish@...
        with:
          password: ${{ secrets.PYPI_API_TOKEN }}
```

Long-lived API tokens are a security risk. PyPI Trusted Publishers (OIDC) eliminate the need
to store a long-lived secret.

**Self-contained fix**: On PyPI, go to the project settings → "Publishing" → add a
"Trusted Publisher" for the GitHub Actions workflow. Then update the workflow to:
```yaml
    permissions:
      id-token: write
    ...
      - name: Publish package
        uses: pypa/gh-action-pypi-publish@v1
```
Remove `PYPI_API_TOKEN` from GitHub Secrets after migration.
